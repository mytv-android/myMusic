摘要

把“平台切换”从用户反复操作，变成系统在后台完成的一次解析。用户看到的是一首歌；系统知道它可能存在于多个平台，并在播放时选择当下最合适的那一个音源。

01 / SEARCH

聚合搜索

并行调用已启用平台的 searchSongs，按“作品”合并为一张结果卡。平台标签可展开，用户能看到每个平台的版本、音质与可用状态。

02 / PLAY

换源播放

A 平台榜单只提供曲目元数据。播放时按策略在 B 平台检索同一版本，取 B 平台自己的播放地址；失败按优先级回退，并在播放器里说明当前音源。

03 / TRUST

状态透明

完整、试听、VIP、无版权、未检测分开表达。试听片段不会被静默当成完整歌曲播放；所有自动降级都有明确文案。

核心判断：“跨平台播放”不是把 A 平台的会员权益转移到 B 平台，而是在 B 平台重新检索同一录音，并使用 B 平台返回的播放地址。因此，B 平台必须有该曲目、用户必须具备对应权益，方案才能播放。这个边界必须在产品文案和技术实现中保持一致。

01

目标与非目标

用户故事

US-1 · 搜索

我在搜索框输入“晴天”，希望一次看到网易云、QQ、酷狗等平台的结果，而不是来回切换平台重复搜索。相同歌曲只需要出现一次，点开后能看到各平台来源。

US-2 · 榜单

我在 QQ 音乐巅峰榜看到一首歌，但想用网易云播放。我点“换源”，选择网易云；如果网易云有完整版就直接播，没有就告诉我原因，并可以换另一个平台。

US-3 · 电视

我在电视上用遥控器操作。所有换源操作都能通过方向键和确认键完成，不依赖长按、拖拽或精细触摸。

US-4 · 失败

播放中途音源失效时，播放器自动换到另一个平台，并从原来的进度继续；如果都不可用，明确告诉我可以打开平台 App，而不是只显示“播放失败”。

目标

编号目标衡量方式
G1一次搜索返回多平台单曲结果，并按作品去重合并≥3 个平台有结果时，同一录音只出现一个主结果卡
G2任意榜单 / 歌单曲目可以选择任意已启用平台播放用户显式选择 B 后，B 有完整音源时可直接播放

非目标

N1 · 权益转移：不把 A 平台的会员、购买或版权权益“转移”到 B 平台。换源播放的前提是 B 平台自身返回可播放地址，且用户具备对应权益。

N2 · 账号互通：不做统一登录、账号绑定或跨平台身份映射。每个平台继续使用自己的 Cookie / 扫码登录。

N3 · 写操作聚合：不向第三方平台写入歌单、收藏或播放记录。第三方写接口不稳定，且容易造成用户数据不一致。

N4 · DRM 绕过：不实现任何 DRM 解密、会员绕过或试听片段伪装。上游库的能力边界就是本应用的能力边界。

N5 · 云端代理：不搭建集中式解析服务，不把 Cookie 或播放地址上传到服务器。

N6 · 100% 匹配承诺：不承诺每首歌都能在其他平台找到。匹配失败是正常状态，界面必须允许它发生。

成功指标（建议）

匹配质量

在 200 首人工标注样本上，自动合并精确率 ≥ 95%，召回率 ≥ 85%；Live / Remix / 伴奏不得被自动合并进录音室版。

播放成功率

在 B 平台确实拥有该曲目的样本中，用户选择 B 后的播放成功率 ≥ 90%。

体验

最快平台结果 ≤ 1.5s 出现；全部平台上限 6s；部分失败不影响其余结果展示。

技术约束

桥接调用是同步阻塞的

GoMobile 的调用运行在 IO 线程。withTimeoutOrNull 可以让 UI 不再等待，但底层调用可能仍在执行。聚合层必须限制并发，不能因为用户连续输入而无限堆积请求。

搜索接口当前没有分页参数

searchSongs(provider, cookie, keyword) 只返回平台默认的第一页。MVP 的聚合搜索按“第一页合并”设计；“加载更多”需要在桥接层补充分页参数后再做。

播放地址没有统一下发元数据

downloadUrl 只返回字符串，没有试听标记、过期时间或格式信息。Apple Music 固定为 30 秒试听；汽水音乐在缺少本机签名器时可能回退试听。MVP 用平台能力表加启发式标记，后续建议扩展桥接。

平台元数据质量差异很大

酷我榜单歌曲经常没有封面；B 站标题夹带上传者、画质和“官方 MV”等噪声；Apple 的时长可能是预览时长；汽水的会员曲目在无签名器时只给片段。匹配器需要按平台做例外处理。

为什么放在 Kotlin

现有桥接已经暴露了所有需要的平台原语。聚合是编排与策略问题，放在 Kotlin 可以快速迭代、方便测试，也避免修改 Go 库和重新编译 GoMobile 绑定。

为什么不新增服务端

所有平台调用已经在设备上完成。新增服务端只会增加部署、合规和 Cookie 风险，也不会改善平台接口本身的可用性。

五条设计原则

P1 · 平台是唯一事实来源

聚合层不编造曲目、不缓存音频、不代理请求。元数据与播放地址都以平台返回为准。

P2 · 元数据合并与音频解析分离

“这首歌是不是同一首”和“现在能不能播”是两个阶段。匹配成功不代表可播放。

P3 · 保守合并

宁可把疑似版本放进“其他版本”，也不把 Live、翻唱或伴奏自动合并进录音室版。

P4 · 渐进与可取消

先到先显示，不让最慢的平台阻塞全部结果；新查询立即取消旧任务。

P5 · 不静默降级

试听、VIP、无版权、超时都必须有明确状态。用户永远知道当前播放来自哪里。

P6 · 本机优先

Cookie、匹配结果、搜索历史都在本机。没有云端账号，也没有跨设备同步。

Canonical ID 的取舍：使用确定性哈希可以让同一首搜索结果在多次查询中保持稳定，也方便 Room 去重。但它假设“标题 + 主歌手 + 版本 + 时长区间”能代表一首歌；如果两个不同录音恰好落入同一区间，需要人工拆分。因此 ID 只用于分组，不作为版权或平台实体标识；平台实体仍以 providerId:songId 为准。

05

曲目匹配

匹配器决定“两张平台结果卡是否合并”。它是整个方案里最容易出错、也最值得保守的部分。

处理流水线

1
Unicode 归一化

NFKC、大小写折叠、全角转半角、统一引号与破折号、去除零宽字符。

2
版本标签提取

识别 Live、Remix、Acoustic、Instrumental、Demo、Cover、DJ、伴奏、现场、翻唱、纯音乐、女声版等，归入 VersionKind。

3
标题清洗

移除 feat. / ft. 片段、电视剧 / 电影说明、上传者与画质噪声、开头曲目编号、括号中的非版本装饰。

4
歌手拆分

按 /、&、feat.、with、逗号、顿号拆分，生成歌手集合；保留主歌手顺序。

5
生成比较键

标题键、歌手集合、版本、时长区间。比较键只用于匹配，不覆盖展示原文。

分组算法

搜索结果规模不大（默认 5 个平台 × 每平台约 20 首 = 100 首），可以直接做带阻塞的配对，不需要复杂索引。榜单批量匹配时才需要缓存。

fun group(results: Map<String, List<Song>>): List<CanonicalTrack> {
    val groups = mutableListOf<Group>()
    for ((providerId, songs) in results) {
        for (song in songs.distinctBy { it.key }) {
            val key = normalize(song)
            val candidates = groups.filter { candidate ->
                candidate.blockKey == key.blockKey ||
                candidate.version == key.version
            }
            val best = candidates.maxByOrNull { score(key, it.key) }
            if (best != null && best.score >= threshold) {
                best.add(providerId, song, best.score)
            } else {
                groups += Group(key, providerId, song)
            }
        }
    }
    return groups.map { it.freeze() }
}

搜索流程

1
输入与去抖

用户停止输入 300ms 后更新建议；按下搜索键才发起完整聚合请求。空查询不请求。

2
快照平台集合

读取设置中的已启用平台，过滤 ProviderInfo.search == true 的平台，最多 6 个并发；超出部分排队。

3
并行 fan-out

每个平台一个协程，单平台超时 6 秒。新查询立即取消旧任务；旧结果不再写入状态。

4
增量到达

每个平台返回后立即更新平台状态与结果快照，不等待最慢的平台。

5
分组与排序

每批结果到达时增量分组；搜索完成后按综合分排序。用户已经滚动时不强行重排。

6

fan-out 的结构示意。实际实现使用 supervisorScope，单个平台失败不影响其他平台。

fun search(query: String, providers: List<ProviderInfo>): Flow<SearchUpdate> = channelFlow {
    val scopeProviders = providers.filter { it.search }.take(6)
    supervisorScope {
        scopeProviders.forEach { provider ->
            launch(Dispatchers.IO) {
                val started = System.currentTimeMillis()
                val result = runCatching {
                    withTimeoutOrNull(6_000) {
                        repository.searchSongs(provider.id, cookie(provider.id), query)
                    }
                }
                send(
                    SearchUpdate.ProviderArrived(
                        providerId = provider.id,
                        songs = result.getOrNull().orEmpty(),
                        elapsedMs = System.currentTimeMillis() - started,
                        error = result.exceptionOrNull()?.message,
                    )
                )
            }
        }
    }
}

桥接取消注意：GoMobile 的底层调用是同步的，协程超时后调用线程可能仍在执行。必须用有界并发（例如全局 3 个槽位）限制同时在途的桥接调用；否则连续搜索会堆积线程和请求。

解析器

class SourceResolver(
    private val repository: MusicRepository,
    private val cookies: () -> Map<String, String>,
) {
    suspend fun resolve(track: CanonicalTrack, policy: SourcePolicy): Resolution {
        val attempts = mutableListOf<Attempt>()
        for (source in order(track.sources, policy)) {
            if (!policy.accepts(source, cookies())) {
                attempts += Attempt(source, "skipped")
                continue
            }
            val cookie = cookies()[source.providerId].orEmpty()
            val url = runCatching { repository.downloadUrl(source.song, cookie) }
                .getOrElse { "" }
            if (url.isBlank()) {
                attempts += Attempt(source, "no-url")
                continue
            }
            return Resolution.Ready(source, url, source.isPreview)
        }
        return Resolution.None(
            attempts = attempts,
            deepLink = track.sources.firstOrNull()?.song?.link.orEmpty(),
        )
    }
}

不要在解析器里做无限回退。每个候选源最多尝试一次；失败后写入短期负缓存，避免用户点一次播放就触发十几个平台请求。所有尝试都要有上限和可解释的失败原因。

private fun onPlayerError(error: PlaybackException) {
    if (failoverInProgress) return
    val position = player.currentPosition
    failoverInProgress = true
    viewModelScope.launch {
        val next = resolver.nextSource(currentTrack, excluding = currentSource)
        if (next != null) {
            player.setMediaItem(mediaItem(next), position)
            player.prepare()
            player.play()
            notice("已切换到 ${next.providerName}，从 ${format(position)} 继续")

            player.pause()
            showNoSourceDialog()

    }
}

队列语义

顺序不变

换源不改变榜单顺序。第 7 首仍然是第 7 首，只是它的播放源可能从 A 变成 B。

逐首独立

每一首可以有不同的 pinnedProvider。用户把第 3 首固定为酷狗，不会影响第 4 首自动选择网易云。

回退不跳歌

B 解析失败时优先回退到 A，而不是直接跳到下一首。只有用户开启“跳过不可播”时才跳过。

歌词与下载跟随播放源

歌词优先从当前播放源获取；为空时回退到原榜单平台。下载必须显式选择来源，文件名带平台标识，避免不同版本互相覆盖。

深链兜底

当所有平台都没有可播放地址时，使用 Song.link 打开平台 App 或网页。手机端用 Intent.ACTION_VIEW；没有处理程序时复制链接并提示。电视端不强行唤起浏览器，显示可扫码的地址或提示在手机上打开。

与 Media3 的衔接

懒解析的边界：Media3 的媒体项需要 URI。现有实现是在 onMediaItemTransition 中解析并替换媒体项。聚合后队列里会有更多未解析曲目，建议：开始播放时至少解析当前 + 下一首；其余在切换时解析。若实测发现替换时机不稳定，再考虑 ViewModel 驱动的单曲播放队列或自定义 MediaSource，不要在第一版就引入复杂媒体源。

验收清单

  • 聚合搜索：搜索“晴天”，至少 3 个平台返回时，同一录音只出现一个主结果卡；展开可以看到各平台来源。
  • 部分失败：一个平台超时或报错时，其余平台结果正常显示，状态行准确说明原因。
  • 来源选择：主结果卡可以打开来源面板，看到每个平台的音质、可用状态和匹配提示。
  • 单曲换源：在 QQ 榜单选择一首歌，选择“用网易云播放”；网易云有完整音源时成功播放，播放器显示“播放源：网易云音乐”。
  • VIP：目标平台为 VIP 且未登录时，显示“需要会员 / 登录”，不显示通用“播放失败”。
  • 试听：Apple Music 来源标记“试听”；默认不自动播放；用户允许后播放并明确提示 30 秒。
  • 中途失败：播放中音源失效时，自动切换到下一候选，并从原进度继续；提示当前平台和续播位置。
  • 全部失败：没有可用源时，显示平台链接 / 深链兜底，不无限重试。
  • 匹配保守：Live、Remix、伴奏、翻唱不自动合并进录音室版；疑似版本进入“其他版本”。
  • 整榜换源：显示匹配率与未匹配曲目；未匹配曲目仍可按原平台播放；可取消批量任务。
  • 迁移：Room v1 → v2 升级后，收藏、历史、下载、本地歌单完整保留。
  • 电视：遥控器可完成搜索、来源选择、播放、换源；焦点可见，目标 ≥ 48dp。
  • 隐私：日志中不出现 Cookie、完整播放 URL、用户搜索词。
  • 兼容：Android 6.0 设备可安装运行；无新增平台专属依赖。

完成的定义：不只是“代码能跑”。需要匹配器标注集回归通过、Room 迁移测试通过、五平台手工验证完成、电视端遥控器走查完成，并且所有降级状态都有对应文案。

D4榜单默认按需换源，不默认整榜匹配减少请求量，避免打开榜单就发上百个请求
D5试听默认不自动播放避免用户误以为在听完整歌曲
D6默认启用 5 个平台覆盖主流曲库，同时控制 fan-out 规模
D7URL 只存内存，不进 Room地址短期有效，持久化没有价值且有隐私风险

D · 一句话总结

让“一首歌”成为核心对象，让“平台”成为可替换的音源。搜索时合并元数据，播放时解析音源；能播就播，不能播就说清楚为什么。这是本方案的全部。

已知限制

超时：原生层使用 OkHttp 的 suspendCancellableCoroutine，协程取消会调用 Call.cancel()，6 秒超时现在是硬超时；底层仍受连接/读取超时约束。

搜索分页：默认 5 个平台（网易云、QQ、酷狗、酷我、咪咕）已支持聚合分页；其余平台目前只返回第一页。

范围：单曲、专辑、歌单均支持聚合搜索；歌单只做“同名歌单”推荐，不合并歌单内容。人工拆分与合并均已实现，合并只影响本机。

歌词：逐词卡拉 OK 取决于音源是否返回增强 LRC；大多数平台只返回逐行时间戳。

平台限制：Apple Music 仍只有试听；Android 原生层无法使用汽水音乐官方签名器，会员曲目通常只能试听。

明文流量：部分平台的封面和音频 CDN 使用 http://，应用启用了 usesCleartextTraffic 才能加载网易云封面等资源；这会在不可信网络下增加被窃听的风险，后续可改为按域名白名单的 Network Security Config。
